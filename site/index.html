Phase 1

One request, five stops

Type https://app.team1.test:8443 and this happens. Tap a stop to see the idea, the command and the code.

Look the shop up in a phone book.

Our own DNS server (dnsmasq) turns app.team1.test into the edge Mac's address. It only answers for .test names and never forwards to the internet.

Try it

dig @<DNS_IP> app.team1.test

You will see

app.team1.test.   300   IN   A   <edge-ip>

Where in the code

config/dns/dnsmasq.conf.template:17scripts/roles.sh:23scripts/roles.sh:63

Walk up and knock three times.

The client opens a TCP connection to the edge on port 8443: SYN, SYN-ACK, ACK. If nothing is listening, the knock is refused.

Try it

nc -vz <EDGE_IP> 8443

You will see

Connection to <EDGE_IP> port 8443 ... succeeded!

Where in the code

config/nginx/nginx.conf.template:35scripts/checks.sh:37

The shop shows an ID card signed by an authority you trust.

Our own CA signed a certificate for app.team1.test and api.team1.test. Clients trust that CA, so there is no curl -k anywhere.

Try it

openssl s_client -connect <EDGE_IP>:8443 -servername app.team1.test -CAfile pki/ca.crt

You will see

Verify return code: 0 (ok)

Where in the code

scripts/create-local-ca.sh:49scripts/install-ca.sh:38config/nginx/nginx.conf.template:39

Reception takes your order and picks a kitchen.

nginx ends the TLS session, then forwards the request to Backend A or Backend B in turn. That is a reverse proxy with round-robin load balancing.

Try it

for i in 1 2 3 4; do curl -s https://app.team1.test:8443/api/status; echo; done

You will see

backend A, then B, then A, then B

Where in the code

config/nginx/nginx.conf.template:26scripts/roles.sh:161

The kitchen cooks the answer and signs it A or B.

One tiny Python server. Every reply carries an X-Backend header, so you can always see which kitchen answered.

Try it

curl -i https://app.team1.test:8443/api/status

You will see

{"backend": "A", "owner": "...", "status": "ok"}
X-Backend: A

Where in the code

backends/server.py:68backends/server.py:34

    C

    Isolation

    Live demo

    Only the edge may reach ports 3001 and 3002. We run this live. Rules the script generates:

    # pf rules on a backend Mac (port 3002)
pass in quick on lo0 all
pass  in quick inet proto tcp from { EDGE, STANDBY } to any port 3002
block drop in quick inet proto tcp from any to any port 3002
    ./bin/phase2 isolate on
    scripts/phase2.sh:250scripts/phase2.sh:269scripts/phase2.sh:286scripts/phase2.sh:297

    The one thing left that can still break: the edge nginx. Our fix today is a standby edge plus a DNS cutover. It is manual and takes about one TTL. A real fix is two edges sharing a floating IP (VRRP), or DNS health checks that move the record by themselves.

    Extension F

    Something broke? Ask in this order

    Follow the path of the request. The first stop that fails is the problem.

    1NameDoes the name become an IP?
    dig @<DNS_IP> app.team1.test

    Timeout or wrong IP means DNS: dnsmasq stopped, wrong record, or wrong resolver.

    bin/doctor:36scripts/checks.sh:35
    2DoorCan we knock on the port?
    nc -vz <EDGE_IP> 8443

    Refused or timeout means nginx is down, the port is wrong, or a firewall rule blocks it.

    bin/doctor:39scripts/checks.sh:37
    3IDIs the certificate trusted?
    openssl s_client -connect <EDGE_IP>:8443 -servername app.team1.test -CAfile pki/ca.crt

    A verify error means the CA is not installed, the name does not match, or the certificate expired.

    bin/doctor:42scripts/checks.sh:38
    4AnswerDoes the site reply?
    curl -i https://app.team1.test:8443/api/status

    502 means the edge is up but both backends failed. One backend down still works.

    bin/doctor:68scripts/checks.sh:42

    ./bin/doctor runs this whole chain and names the first failing stop. ./bin/phase2 drill hides a fault for us to practise on.
